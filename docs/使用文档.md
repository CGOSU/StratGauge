# StratGauge 使用文档

> 面向研究人员和本地运维者的可执行说明。所有示例均假设当前目录为 `backend/`，并设置了 `PYTHONPATH=src`。

## 1. 先读这几条边界

- StratGauge 是半自动研究和记录工具，不连接券商，不创建、修改或取消真实订单。
- 当前行情数据只有日线；收盘后产生的信号最早从下一交易日开始处理。
- 通达信负责执行选股公式，StratGauge 只保存导出文件和公式元数据，不解析或执行通达信公式。
- 所有时间点数据都必须区分 `session_date`、`available_at`、`created_at`/`ingested_at` 和调用方的 `as_of`。交易日早于选股日，不代表数据在当时已经公开可用。
- 原始响应、规范化行情、质量报告、公式、批次、人工标签、客观结果、特征和模型工件均按不可变或追加式证据保存；已有文件通常拒绝覆盖。
- 未成交、数据不足和未解决不等于亏损；统计和训练准入不会把它们静默填成零收益。

## 2. 快速开始

### 2.0 一键启动前后端

完成依赖安装后，推荐从仓库根目录运行统一启动器：

```bash
uv run --project backend python start.py
```

Windows 可双击根目录的 `start.cmd`。启动器并发运行后端和前端，日志分别带 `[backend]`、`[frontend]` 前缀；默认地址为 `http://127.0.0.1:8000` 和 `http://localhost:5173`。若 Windows 保留了 8000 端口，启动器会自动切换后端到备用端口 8091，并同步前端代理。按 `Ctrl+C` 或关闭控制台时会清理 Uvicorn reload、pnpm、Vite 及其子进程；任一服务启动/运行失败时会停止另一个服务并返回非零退出码。启动器只编排已有命令，不自动安装依赖、不自动打开浏览器。

常见失败：`uv`、Corepack/pnpm 或前端 `node_modules` 缺失时，请先按下面的安装步骤补齐；后端若出现 `No module named 'stratgauge'`，请使用带 `--app-dir src` 的命令。需要单独排错时，分别启动后端和前端：

```bash
# backend/
uv run uvicorn stratgauge.api.app:app --reload --app-dir src

# frontend/
corepack pnpm dev
```

### 2.1 安装后端

```bash
cd backend
uv sync --all-groups
```

默认依赖包含 FastAPI、DuckDB、Polars、Pydantic、Uvicorn；`live-data` 才安装 AKShare/BaoStock，`ml` 才安装 LightGBM：

```bash
uv sync --extra live-data
uv sync --extra ml
```

默认测试不访问网络。启动 API：

```bash
uv run uvicorn stratgauge.api.app:app --reload --app-dir src
```

### 2.2 启动前端

```bash
cd frontend
corepack pnpm install --frozen-lockfile
corepack pnpm dev
```

当前前端默认把 `/api` 代理到本地 API；也可以设置 `VITE_API_BASE_URL` 指向一个完整 API 前缀。前端日期时间控件使用浏览器本地值 `YYYY-MM-DDTHH:mm`，提交时固定补成 `YYYY-MM-DDTHH:mm:00+08:00`。

### 2.3 环境变量

| 变量 | 何时需要 | 作用 |
| --- | --- | --- |
| `TUSHARE_TOKEN` | Tushare 日线、复权因子、股票主数据、Tushare 交易日历 | 只从环境读取，不写入请求快照、日志或文档。 |
| `WAIZAO_TOKEN` | 选择 `waizao` 作为单票日线源 | 只从环境读取；歪枣网当前按证券代码逐票请求。 |
| `VITE_API_BASE_URL` | 前端 API 不在 `/api` 代理下时 | 前端请求的 API 前缀；末尾 `/` 会被移除。 |

## 3. 时间、代码和数字输入约定

### 3.1 日期与日期时间

- `date`：严格使用 `YYYY-MM-DD`，例如 `2026-08-10`。
- 带时区的 `datetime`：使用 ISO-8601，例如 `2026-08-10T17:00:00+08:00` 或 `2026-08-10T09:00:00Z`。后端拒绝无时区的时间。
- 前端的 `datetime-local` 不是带时区的字符串；浏览器表单值会由前端按北京时间追加 `+08:00`。
- `--as-of`、`--exported-at`、`--imported-at`、`--recorded-at`、`--evaluated-at`、`--labeled-at`、`--changed-at`、`--registered-at`、`--compared-at`、`--scored-at` 和 API 中相应字段都必须带时区。
- 交易日历文件中的日期必须唯一、升序排列；空行和 `#` 后的注释会被忽略。

### 3.2 证券代码

- 内部标准标识是 `六位代码.交易所`，交易所只能是 `SH`、`SZ` 或 `BJ`，例如 `000001.SZ`。
- 普通六位代码不允许靠前缀猜交易所；CSV/TSV/TXT 必须有交易所列、代码后缀，或使用通达信固定行情表格式。
- `.EBK` 使用七位市场前缀：首位 `0`=SZ、`1`=SH、`2`=BJ，后六位为代码，例如 `1600593` 解析为 `600593.SH`。
- 通达信行情表在没有交易所列且第一列为代码、同时包含版本化名称表头（如 `名称(4)`、`名称(5)`）和 `涨幅%` 表头时，按首位命名空间映射：`0/3`=SZ、`6`=SH、`4/8`=BJ。普通表格仍不能仅凭六位代码推断交易所。

### 3.3 Decimal、整数和重复参数

- 金额、价格、覆盖率等 Decimal 输入必须是有限数字；金额和价格通常要求大于 0。
- “正整数”不接受小数；重试次数允许 `0`。
- CLI 中标记“可重复”的参数使用 `action=append`，每次出现都会追加一项；例如多个 `--benchmark` 或 `--symbol`。
- API 请求模型使用 `extra="forbid"`，多传字段会被拒绝，不会静默忽略。

## 4. 行情源：什么时候联网，什么时候读本地

这是本项目最重要的操作规则。所谓“写入本地快照”不等于“下一次一定从本地读取”；是否联网由调用入口决定。

### 4.1 总体决策表

| 操作 | 默认数据入口 | 命中本地条件 | 命中后行为 | 未命中时行为 |
| --- | --- | --- | --- | --- |
| `sync_tushare_calendar.py` | Tushare `trade_cal` | 请求区间完整落在已有 calendar manifest 的覆盖区间内，且文本和 manifest 哈希有效 | 读取本地交易日文件，不调用 Tushare | 只请求覆盖区间外的左/右缺口，合并后原子写入文件和 manifest |
| `sync_backup_calendar.py` | BaoStock + AKShare | 同上 | 读取本地双源校验后的日历，不调用两个供应商 | 对每个外部缺口同时请求 BaoStock 和 AKShare；集合不一致则保留原始证据但不发布缓存 |
| `sync_tushare_universe.py` | Tushare `stock_basic` | 没有“自动按请求复用”的跳过分支 | 不适用；每次运行都会调用所选状态的 `stock_basic` | 远程请求 `L` 或 `L/D/P`，内容相同的参考快照在存储层按内容 ID 复用 |
| `sync_tushare_daily.py` | Tushare `daily(trade_date=...)` | 存在同一 provider、交易日、已批准 universe snapshot 的 `market_daily` 快照 | 读取已批准全市场 Parquet；该日不再请求 `daily` | 远程请求全市场日线，通过质量门后写入 raw/Parquet/manifest |
| `sync_tushare_daily.py` 的复权阶段 | Tushare `adj_factor` | 同日市场日线刚通过质量门，并且同 provider、同交易日、同股票池、同 source daily snapshot 的因子快照已批准 | 读取已批准因子快照 | 远程请求 `adj_factor`；日线快照未批准时不会请求因子 |
| `backfill_tushare_adjustment_factors.py` | Tushare `adj_factor` | 已存在匹配的批准因子快照 | 本地跳过 | 只有存在同 provider、同交易日、同股票池的批准 market daily 快照时才远程请求；缺日线只记录 `missing_daily_snapshot`，绝不补抓日线 |
| `mature_tdx_selection.py` | 选定 provider 的单票日线 | 无本地预查 | 不适用；每个候选都调用适配器 | 逐候选远程请求 `start=选股日+1` 到 `end=evaluated_at.date()` 的日线，再把结果写入本地快照 |
| `backfill_selection_history.py` | 选定 provider 的单票历史日线 | 仅交易日历可以从本地读；行情快照没有预查复用分支 | 读取本地 sessions 文件/日历缓存，行情仍请求 provider | 逐候选、基准、行业标的远程请求选股日前的回看区间 |
| Web `POST /v1/selection-batches/{id}/mature` | 选定 provider 的单票日线 | 无本地预查 | 不适用；同步调用 provider | 远程逐候选抓取，结果写入本地 |
| Web 成熟任务 `market_data_mode=provider` | 任务中的 provider | 无本地预查；任务内已有候选结果只按 task/candidate 复用 | 已写入的同任务结果本地复用 | 远程逐候选抓取；网络/限流/超时失败可按 `max_retries` 重试 |
| Web/CLI 成熟任务 `market_data_mode=approved_snapshots` | 已批准全市场快照 | 任务固定保存 `input_market_snapshot_ids` | 只读本地 Parquet 和任务账本，执行不创建 provider 请求 | 缺快照、快照未批准、不可用或股票池不匹配时失败，不回退到 provider |
| API 查询、标签、统计、导出、组合、策略、模型和漂移报告 | 本地 JSON/Parquet/DuckDB | 始终是本地存储 | 不联网 | 缺文件或状态不满足时返回结构化错误 |

### 4.2 交易日历缓存的精确规则

缓存由文本文件和同目录 manifest 组成，例如：

```text
data/calendars/trade-cal-sse.txt
data/calendars/trade-cal-sse.manifest.json
```

缓存读取前会同时检查：文件存在、manifest 可解析、文件日期与 manifest 的 `sessions` 完全一致、日期升序且无重复、内容哈希一致、交易所一致。任何检查失败都是错误，不会用自然日、当前日期或另一个交易所静默替代。

覆盖判断只比较 manifest 的 `start_date` 和 `end_date`。请求范围完全落在边界内时不访问网络；超出左边界或右边界时只拉取外部缺口。当前实现不会用供应商请求去修补覆盖区间内部的“理论缺失日”，因为 manifest 已把现有 session 集合作为缓存事实；如需重新核验完整历史，应删除/迁移到新输出路径后显式重建，并保留旧证据。

Tushare 日历的 `source_providers` 是 `tushare`；备用日历的 `source_providers` 必须包含 `baostock` 和 `akshare`，两个来源的完整交易日集合必须完全一致后才发布。备用缓存不能冒充 Tushare `trade_cal`。

### 4.3 日线快照的精确规则

全市场同步使用以下联合键查找已批准快照：

```text
(provider, session_date, universe_snapshot_id, request_kind=market_daily)
```

命中才返回 `skipped=true` 并读取本地 manifest/Parquet。若快照是 `rejected`、股票池不同、provider 不同、请求日不同或只存在 raw 文件但没有批准 manifest，都视为未命中，需要重新执行 provider 请求。

单票 `ingest()` 当前是“适配器优先”：先调用 `adapter.fetch_daily_bars()`，再将返回内容按 SHA-256 写入快照。相同响应可能生成相同的本地 snapshot ID，但这不会阻止本次远程请求。因此“本地已保存过单票历史”不能推导出成熟或历史补数会离线运行。

### 4.4 独立 `000300.SH` 基准证据

`sync_tushare_index_daily.py` 是独立的 Tushare `index_daily` 基准证据同步入口，只允许证券代码 `000300.SH`（沪深 300 指数），请求类型固定为 `index_daily`。它与普通证券 `daily` 的 `security_daily` 请求、全市场 `market_daily` 请求和复权因子请求分开保存，不能用股票日线或其他指数快照替代。

命令只接受本地显式交易日历；选定区间没有交易日时返回 `status=skipped`，不会伪造日期。已有快照仍按现有 `ingest`/`SnapshotStore` 的不可变、质量门和批准状态处理。该命令只生成可审计的基准快照，不创建成熟结果、特征、训练标签、模型或 shadow 评分。

### 4.5 快照重放与 provider 模式的区别

`queue_selection_maturity_tasks.py` 只扫描本地已批准的全市场行情，要求从选股日之后到 `now.date()` 至少有 `horizon_sessions + 1` 个连续输入交易日，并创建带固定快照 ID 的任务。`run_selection_maturity_tasks.py` 执行这类任务时调用 `run_selection_outcome_snapshot_job()`：只读本地 Parquet，拒绝供应商调用、未来快照、未批准快照、混用股票池或缺少日期的快照。

相反，Web 页面直接创建的成熟任务默认是 `market_data_mode=provider`。它保存的是 provider、评估时间和政策，不保存全市场输入 snapshot ID；执行时会远程逐候选抓取。要实现可复现的离线重放，必须先完成全市场同步、用队列创建 `approved_snapshots` 任务，再运行任务。

## 5. 本地目录和证据文件

默认相对路径相对于执行命令时的当前工作目录；推荐在 `backend/` 下运行脚本。

| 路径 | 内容 | 是否可覆盖 |
| --- | --- | --- |
| `data/tushare/reference/raw/`、`manifests/` | Tushare `stock_basic`/`trade_cal` 原始参考响应及 manifest | 内容相同复用；不同内容生成新 ID |
| `data/calendar/reference/` | BaoStock/AKShare 日历原始响应及 manifest | 内容相同复用 |
| `data/calendars/` | 交易日文本和覆盖 manifest | 通过原子扩展更新；篡改会阻断读取 |
| `data/market/raw/` | 全市场/单票行情原始响应 | 内容寻址 |
| `data/market/normalized/` | 已标准化日线或复权因子 Parquet | 内容寻址 |
| `data/market/manifests/`、`quality/`、`catalog.duckdb` | 快照状态、质量报告、查询索引 | manifest 状态可追加更新，证据文件不覆盖 |
| `data/universe/snapshots/` | 时间点股票池快照 | 不覆盖 |
| `data/selection/tdx/raw/` | 通达信原始字节 | 以文件 SHA-256 命名 |
| `data/selection/tdx/imports/`、`manifests/` | 解析结果和批次索引 | 不覆盖 |
| `data/selection/tdx/formulas/`、`labels/`、`outcomes/` | 公式目录、人工标签和客观结果 | 追加/内容寻址 |
| `data/selection/tdx/maturity_tasks/`、`maturity_task_events/` | 成熟任务状态和事件 | 任务状态物化更新，事件追加 |
| `data/selection-datasets/`、`data/models/` | JSONL 数据集、切分、模型和评估工件 | CLI 默认拒绝覆盖 |
| `data/portfolio/` | 订单、成交、复盘和由成交推导的持仓 | 追加式 |

## 6. 推荐的半手动选股流程

### 6.1 先登记公式

通达信公式目录使用 API `POST /v1/formulas` 创建，或在 Web 数据管理页创建。`register_strategy.py` 登记的是策略版本，不是公式目录。推荐先创建公式，这样导入时可以使用不可变的 `formula_id`。

最小公式请求体：

```json
{
  "name": "我的选股公式",
  "version": "v1",
  "description": "可选的公式说明"
}
```

若还需要登记可供回测/模型引用的策略版本，另行执行：

```bash
PYTHONPATH=src uv run python scripts/register_strategy.py --root data --input strategy.json
```

### 6.2 导入通达信文件

```bash
PYTHONPATH=src uv run python scripts/import_tdx_selection.py \
  --file path/to/selection.txt \
  --selection-date 2026-08-10 \
  --exported-at 2026-08-10T15:05:00+08:00 \
  --formula-name "趋势选股" \
  --formula-version v1 \
  --root data/selection
```

导入时会：读取完整文件字节、计算源文件 SHA-256、按格式解析候选、生成批次 ID、保存 raw 文件、解析 JSON 和 manifest。`--imported-at` 默认当前 UTC 时间；它不能早于 `--exported-at`。导入不会联网，也不会请求行情。

### 6.3 在冻结时间内人工标注

```bash
PYTHONPATH=src uv run python scripts/label_tdx_selection.py \
  --root data/selection \
  --batch-id <batch_id> \
  --candidate-id <candidate_id> \
  --decision watch \
  --labeled-at 2026-08-10T15:10:00+08:00 \
  --note "等待次日确认"
```

`--decision` 只能是 `buy_candidate`、`watch`、`pass`、`invalid`。前端按钮显示为“候选”“观察”“放弃”“无效”，其中“候选”表示下一交易日优先复核，不代表已经成交；“观察”表示暂时不买、继续跟踪。标签必须不早于导出时间，且严格早于“选股日期次日 02:00:00（使用导出时间的时区）”；标签只是当时的人工判断，不是行情胜负或实际成交记录。若第二天没有买、之后才实际买入，应在持仓台账记录真实订单/成交时间和价格，不能用原始标签替代成交记录。

#### Web 可复用标签

“策略信号”页面股票详情中的“新增人工评审”对话框按固定的 `position`（位置）、`pattern`（形态）、`price_volume`（量价）、`sector`（板块）四类展示当前启用的可复用标签。每类输入标签名称后点击“新建并选中”，或在输入框按 Enter，服务端创建标签并立即选中；提交评审时前端只发送 `reusable_tag_ids`，服务端按当前活跃目录生成不可变的 `tag_id/category/label` 历史快照。

数据管理工作区的“可复用标签”目录支持改名、归档和恢复。归档标签不会出现在新的评审选项中，但已有评审仍保留其快照；改名也不会改写历史评审。标签目录和事件追加保存、禁止硬删除。可复用标签当前仅供人工评审和历史展示，不进入 `selection-annotation-dataset-v1`、特征、训练、模型注册、shadow、推荐或交易；若未来用于机器学习，必须另行冻结映射和版本。

### 6.4 选择成熟方式

直接成熟一个批次：

```bash
PYTHONPATH=src uv run python scripts/mature_tdx_selection.py \
  --root data/selection \
  --market-root data/selection-market \
  --batch-id <batch_id> \
  --provider tushare \
  --evaluated-at 2026-08-25T17:00:00+08:00 \
  --horizon-sessions 10 \
  --position-notional 10000
```

这条命令是 provider 模式，会逐候选远程请求日线；`evaluated_at` 必须晚于选股日期。`position-notional` 是费用和收益率计算的名义金额，不能省略或让系统猜测。

若已同步全市场日线，优先使用本地快照重放：

```bash
PYTHONPATH=src uv run python scripts/queue_selection_maturity_tasks.py \
  --root data/selection \
  --market-root data/market \
  --calendar-file data/calendars/trade-cal-sse.txt \
  --provider tushare \
  --horizon-sessions 10 \
  --position-notional 10000 \
  --universe-snapshot-id <universe_snapshot_id>

PYTHONPATH=src uv run python scripts/run_selection_maturity_tasks.py \
  --root data/selection \
  --market-root data/market \
  --limit 1
```

队列命令不联网；它只使用已经批准、同一 provider 和股票池下的全市场快照。`run_selection_maturity_tasks.py --task-id <task_id>` 可以只运行一条指定任务；不传 `--task-id` 时按排队状态取最多 `--limit` 条。

## 6.5 显式补齐 ML 市场证据

`prepare_selection_ml_market_evidence.py` 是唯一负责为选定批次扩展交易日历、补齐全市场日线、同源复权因子和独立 `000300.SH` `index_daily` 证据的编排入口。它必须由操作者显式执行；不会自动成熟候选、生成特征、训练、注册模型、shadow 评分或交易。

先确认使用的 universe snapshot 是显式、已批准且覆盖目标历史的时间点股票池，再执行例如：

```bash
cd backend
$env:PYTHONPATH="src"
uv run python scripts/prepare_selection_ml_market_evidence.py `
  --all-batches `
  --selection-root data/selection `
  --universe-root data `
  --universe-snapshot-id <universe_snapshot_id> `
  --market-root data/selection-market `
  --calendar-cache data/calendars/trade-cal-sse.txt `
  --reference-root data `
  --lookback-sessions 20 `
  --maturity-horizon-sessions 10 `
  --minimum-coverage 0.90 `
  --now 2026-08-25T17:00:00+08:00 `
  --output data/ml-market-evidence/report.json
```

PowerShell 使用反引号续行；在 Bash 中将续行符替换为 `\\`。只处理明确批次时重复 `--batch-id <batch_id>`；也可以用成对的 `--start-date YYYY-MM-DD --end-date YYYY-MM-DD`，日期范围包含端点。`--all-batches` 包含归档批次。`--universe-snapshot-id`、`--market-root`、`--calendar-cache` 和 `--reference-root` 不应省略，以免把当前股票池或错误日历误用于历史范围。

命令输出并可选写入一个不可覆盖的 JSON 报告，包含 `calendar`、`market_daily`、`adjustment_factors`、`benchmark_index_daily` 和 `point_in_time` 阶段。报告会区分已批准快照的 `skipped`、新同步的 `approved`、质量拒绝、provider 失败、缺失日线和阻断原因；退出码 `0` 仅表示四类证据阶段均达到批准条件，非零只表示本次报告未达到研究就绪，不会把缺失数据填成成功。首次运行可能访问 Tushare `trade_cal`、`daily`、`adj_factor` 和 `index_daily`，仅从环境变量读取凭据；默认测试、`--help` 和本地已有批准快照命中不会访问 provider。

安全边界：市场快照的 `available_at` 仍由实际抓取时间记录，补抓历史行情不能证明它在历史选股/评审时已经可见。命令拒绝 universe `as_of` 晚于任一目标交易日，并保留日历、质量门和 provider 错误；报告中的 `feature_visibility_guaranteed` 永远不会替后续特征阶段作承诺。只有在标签成熟、行情/因子/独立基准证据和各项时间点检查齐备后，才由操作者继续执行 `build_selection_training_feature_snapshots.py`，再进入 join、训练及后续人工阶段。

## 6.6 四用途 ML 人工研究流程

这一节只说明阶段顺序和证据如何传递；每个 CLI 的完整参数表仍在第 7.3 节，不在这里重复。

### 操作图

```text
readiness / 已授权数据
        ↓
export_selection_ml_datasets.py
        ↓  四类原始 JSONL（每个用途单独一份）
prepare_selection_training_dataset.py × 4
        ↓  labels/{train,validation,test,purged}.jsonl + manifest/readiness
build_selection_training_feature_snapshots.py × 4
        ↓  feature-root 下的 FeatureSnapshot + output/report.json
join_selection_training_features.py × 4
        ↓  joined/{train,validation,test}.jsonl + join-report/manifest
        ├─ train_selection_feature_baseline.py × 4（参考基线）
        └─ train_selection_feature_lightgbm.py × 4
                ↓
        calibrate_selection_feature_probabilities.py × 4（只用 validation 拟合）
                ↓
        register_selection_feature_model.py × 4（人工注册 challenger）
                ↓
        transition_selection_feature_model.py × 4（人工 challenger → shadow）
                ↓
        准备无标签 shadow JSONL + 精确 source-input-sha256
                ↓
        score_selection_feature_shadow.py × 4
                ↓
        validate_selection_feature_walk_forward.py × 4
                ↓
        compare_selection_feature_models.py（只比较 validation 证据）
```

其中 `× 4` 表示分别对 `candidate_success`、`annotation_decision`、`buy_timing`、`sell_timing` 执行四次；每次请求只能包含一个用途。baseline 与 LightGBM 是同一 joined 输入上的两条人工触发分支，校准只接收 LightGBM 输出。注册、transition、shadow、走步和 compare 不会被前一阶段自动调用。

### 输入/输出关联和时间点边界

1. readiness 通过后，先用 `export_selection_ml_datasets.py` 形成四类原始 JSONL；候选成功率、人工评审、买入择时和卖出择时不得混成一个标签契约。
2. `prepare_selection_training_dataset.py` 的输出目录是后续 `--labels-dir`；它固定保存 train/validation/test/purged 及 manifest。`purged` 永不进入训练、校准、走步或比较。
3. `build_selection_training_feature_snapshots.py` 必须由操作者重复提供已批准的 `market_daily`、独立 `000300.SH` `index_daily` 以及（如采用）有正确血缘的 `adjustment_factor` snapshot ID。它不扫描目录、不联网、不调用 join/训练，并把标签的 `observation_date` 写入 `FeatureSnapshot.selection_date`：annotation/buy/sell 的 `as_of` 使用 `observation_at`，candidate_success 缺省时仅从不可变批次 `exported_at` 派生。输出报告中的 `source_label_dataset_sha256`、snapshot ID 和逐样本失败是后续审计输入。
4. `join_selection_training_features.py` 的 `--feature-snapshot-id` 必须显式对应上一步报告中的映射；输出目录同时保留标签分区、特征分区、连接报告和 manifest。连接失败不得用零值或当前行情补行。
5. baseline/LightGBM 的输出目录必须分开且不可覆盖。两者只用 train 拟合，validation/test 只评估；LightGBM 的 `model.txt`、`model.json`、预测和 manifest 是校准、注册、shadow 和走步共同引用的同一训练证据。
6. `calibrate_selection_feature_probabilities.py` 只用 validation 拟合校准器；test 可以产生隔离评估，但不得反向影响校准参数。注册时 `--training-dir` 与可选 `--calibration-dir` 必须来自同一用途、同一特征/标签血缘。
7. 注册结果固定从 `challenger` 开始。操作者必须单独执行 `transition_selection_feature_model.py` 才能进入 `shadow`；没有该人工事件，shadow CLI 应拒绝运行。当前新用途链没有 `active` 自动晋升路径。
8. shadow 输入必须人工或由外部离线脚本准备为 UTF-8 JSONL：每行只包含候选 ID、用途、对应 `label_contract_id` 和无标签 `FeatureSnapshot`。禁止放入 `label`、结果状态、`net_return`、`label_available_at` 等监督信息。先固定 canonical JSON 序列化和 LF 换行，再对**实际提交给 CLI 的完整字节**计算 SHA-256；`--source-input-sha256` 不得使用另一份文件或重新格式化后的内容。shadow 报告写入独立的 `shadow-scores/`，并永久标记 `used_for_decision=false`。
9. 走步使用显式 folds 和已注册用途模型；每折只在开发期 train 数据内重训，validation 才产生比较指标，final-test 只保留隔离边界和计数。compare 的政策、注册 ID 和走步报告 ID 必须由操作者显式提供；它只生成审阅证据，不改变生命周期。

### 推荐证据目录

```text
data/
├── ml-datasets/                         # export 的四类原始 JSONL
├── ml-training/<purpose>/                # prepare：labels 与 readiness
├── ml-features/<purpose>/                # join：特征 split、join report、manifest
├── ml-models/<purpose>-feature-baseline/ # baseline（参考，不自动注册）
├── ml-models/<purpose>-lightgbm/         # LightGBM：model.txt/json、预测、manifest
├── ml-calibration/<purpose>/             # validation-only calibration
└── models/feature-registry/
    ├── registrations/                    # 注册副本和 challenger 事件
    ├── shadow-scores/                    # 非权威 shadow 报告
    ├── walk-forward-reports/             # 走步证据
    └── comparisons/                      # validation 比较证据
```

目录名可以按项目运维约定调整，但每个阶段应使用新的目标路径；既有工件只允许字节完全相同的重放，不允许原地覆盖。Windows Task Scheduler 可以逐条调用这些 CLI，但调度器只负责启动明确命令，不代表阶段自动串联。真实行情收集、LightGBM 依赖安装、训练、注册和 shadow 运行均需研究负责人另行授权；本地默认测试和离线演练不访问 provider、不使用凭据，也不写入 `backend/data`。

#### Web：机器学习前置检查

导入数据页的“机器学习前置检查”卡片调用只读接口：

```text
GET /v1/ml/readiness
```

卡片展示候选成功率用途的已成熟 `win/loss/flat` 数量、`success/not_success` 类别、待成熟/未入场/未解决数量、样本缺口、特征快照、基准、复权因子和用途模型证据。默认至少需要 100 条已成熟标签、两个类别、单一 tracking/outcome policy，并且特征、独立 `000300.SH` `index_daily` 基准和候选复权因子证据齐全，才会显示“可以开始训练”。

当前卡片只读和可刷新，不会启动训练、注册模型、选择模型或启用 shadow。达到训练前置门后，仍需人工按 `export → prepare → split → join → train` 执行 CLI；LightGBM 需要显式安装 `ml` 可选依赖。模型注册和 `challenger → shadow` 迁移仍是后续人工步骤，shadow 分数不用于决策。

#### Web：成熟结果列表

导入数据页在机器学习前置检查卡片之后提供独立的“成熟结果列表”。它是跨全部历史候选的只读投影，默认包含归档批次和已经排除的候选，用于核对与前置检查相同的候选范围；它不是成熟任务创建、执行或行情同步入口。页面只发起下面的 GET 请求，不发起行情、成熟、训练、评分或交易写请求：

```text
GET /v1/selection-maturity/page
```

可选查询参数如下：

| 参数 | 默认值 | 约束 |
| --- | --- | --- |
| `status` | 不传（全部） | `pending`、`win`、`loss`、`flat`、`no_entry`、`unresolved` |
| `page` | `1` | 大于等于 1 |
| `page_size` | `50` | 1—200 |

响应沿用 `items`、`page`、`page_size`、`total`、`has_next` 分页契约，并额外返回始终按全部历史范围统计的 `status_counts` 六类汇总。每条记录包含批次、候选、当前状态、最新结果证据、tracking policy、批次归档状态和候选排除信息；同一候选在多个 tracking policy 下会保留多条记录，并按每个 policy 的最新结果展示。

`pending`（页面显示“待成熟”）表示候选没有任何客观结果，不等于输或未入场。`no_entry`（未入场）和 `unresolved`（未解决）表示已有明确结果状态，但都不进入候选成功率训练的 `win/loss/flat` 标签；不能把它们填成亏损或零收益。列表用于查看证据，不改变成熟任务账本、客观结果文件或 shadow 评分边界。

#### `export_manual_position_tracking_dataset.py`

该命令导出独立的手工持仓跟踪 evidence，不是 `export_selection_ml_datasets.py` 的第五个用途，也不会把手工台账伪造成 `SelectionCandidate`。它只读取本地跟踪案例、订单/成交/复盘和 approved `market_daily` 快照，不创建 provider、不访问外部行情、不连接券商。

```bash

```

| 输入 | 必填/默认 | 约束 |
| --- | --- | --- |
| `--portfolio-root` | `data` | 读取 tracking case、订单、成交和复盘账本 |
| `--market-root` | `data/selection-market` | 只读取 approved `market_daily` 快照，不触发 provider |
| `--evaluated-at` | 必填 | 带时区 ISO datetime；过滤未来事实和晚于该时点不可用的行情 |
| `--output-dir` | 与 `--output`/`--dataset-output` 三选一 | 目录输出 dataset 与 report |
| `--output`/`--dataset-output` | 可选 | `.json`、`.jsonl` 或目录路径；用于指定 dataset 文件 |
| `--report`/`--report-path`/`--report-output` | 可选 | `.json` 或目录路径；用于指定 report 文件 |

导出行固定为 `manual-position-tracking-dataset-v1`，报告固定为 `manual-position-tracking-report-v1`。新手工确认买入使用默认 `manual-position-tracking-v1` 案例；历史持仓必须先由用户显式“纳入跟踪”，登记时间是 `tracking_started_at`，不会改写旧订单/成交。手工确认卖出不要求选择跟踪案例；有单个可推断案例时系统仍可自动关联，明确选择案例时继续校验证券和剩余数量。未关联的卖出不纳入跟踪 evidence，但不阻断真实交易记录。数据集只收集开始时间之后、明确关联案例的订单/成交/复盘和评估时间前已批准的本地行情；登记前事实仅作来源审计。候选、策略或推荐关联的订单/成交、未来事实，以及无法唯一归属案例的复盘会排除并在报告中保留原因；卖出理由随 evidence 行保留。

报告按案例统计 evidence 行、手工/市场覆盖、缺失和排除原因、`eligible`/`not_eligible` 资格及源事实 SHA-256。缺少手工证据或市场证据的案例会使 `ready=false`；这里的 `ready` 仅表示 evidence 覆盖完整，不表示已有监督标签、特征或模型训练/发布准入。报告和 dataset 已存在时均拒绝覆盖；报告不完整仍保留两个输出并返回退出码 `1`，参数错误、目标冲突或 IO 错误返回 `2`，完整报告返回 `0`。

该导出不接入候选成功率、人工评审、买入择时、卖出择时四用途训练，也不接入训练、注册、shadow、推荐或交易。若未来要用手工 evidence 训练模型，必须另行设计版本化标签/特征契约并由操作者按阶段显式启动。

### 7.2 顺序 GET 接口性能巡检

这是一个独立的只读巡检 CLI，只请求已经运行的 FastAPI 服务，不启动服务、不启动前端、不写入业务数据，也不进行并发压测。它先读取服务的 `/openapi.json`，发现全部 GET 路由，再读取版本化样例 `backend/scripts/benchmark_get_cases.json`；可运行样例会先预热，再按顺序请求多次并输出状态码、响应字节数、中位耗时和最大耗时。响应正文不会写入输出。

先在一个 PowerShell 窗口独立启动后端，并保持该窗口运行：

```powershell
cd D:\Code\Python\StratGauge\backend
$env:PYTHONPATH = "src"
uv run uvicorn stratgauge.api.app:app --app-dir src --host 127.0.0.1 --port 8000 --workers 1
```

再打开另一个 PowerShell 窗口执行巡检：

```powershell
cd D:\Code\Python\StratGauge\backend
$env:PYTHONPATH = "src"
uv run python scripts/benchmark_get_endpoints.py `
  --base-url http://127.0.0.1:8000 `
  --iterations 5 `
  --warmup-requests 1 `
  --timeout 30
```

`--cases` 默认使用 `scripts/benchmark_get_cases.json`；也可显式指定其他版本化清单。`--iterations` 必须至少为 1，`--warmup-requests` 可为 0，预热请求不计入耗时统计。性能门槛按样例的可选 `max_median_ms` 配置；本项目没有把机器相关阈值接入普通单元测试或 CI，因此不要把一次本机耗时当作固定性能承诺。

维护样例时必须遵守以下契约：

- 新增 GET 路由必须在清单中增加可运行样例（填写有效路径/查询参数和期望状态码），或填写具体的 `skip_reason`；不能静默漏测。
- 清单与 `/openapi.json` 中的 GET 路由必须双向精确匹配。缺失项、陈旧项、版本不支持或必填参数未覆盖都会以退出码 `2` 阻断。
- 需要 `batch_id`、`candidate_id`、`job_id`、证券标识、必填日期/时间点或流式下载的接口，若没有稳定测试证据必须显式跳过；不能猜测参数，也不能把 `404`/`422` 当作成功结果。
- 巡检只按单线程顺序发送请求；跳过项不发请求。它不创建批次、标签、行情任务、订单或其他业务数据，也不输出 URL 中的敏感参数或响应正文。

退出码约定：`0` 表示所有可运行样例的 HTTP 状态和可选性能阈值均通过（显式跳过项算通过）；`1` 表示 OpenAPI/接口请求失败、网络错误、非期望 HTTP 状态或中位耗时阈值失败；`2` 表示巡检配置错误，包括样例清单与 OpenAPI 路由不一致。没有连接运行中服务时不会自动启动服务，应先检查后端窗口和 `/healthz`。

### 8.2 手工持仓台账

手工台账记录用户实际订单、成交、持仓和复盘；它本身不代表策略信号。手工持仓跟踪案例是从新买入或历史持仓显式登记时点开始的独立审计范围，采用固定 `manual-position-tracking-v1`，不会产生选股推荐。手工创建研究候选则属于 `SelectionBatch.source=manual`，仍是候选/研究链事实，不能自动变成 tracking case。只有明确关联案例且通过时间点与 approved 行情检查的 tracking evidence 才能进入独立 `manual-position-tracking-dataset-v1`；研究候选继续进入既有四用途导出，按来源保留 `manual`，两者不混合。

| 方法和路径 | 输入 | 行为 |
| --- | --- | --- |
| `GET /v1/positions` | 无 | 读取由成交重放推导的持仓 |
| `GET /v1/workbench/stocks/{symbol}/performance` | path `symbol`；可选 `as_of` | 只读重放单证券历史净收益率和本地行情证据；仅当前活动持仓的详情抽屉使用 |
| `GET /v1/manual-orders` | 无 | 读取本地追加式订单 |
| `GET /v1/manual-fills` | 无 | 读取本地追加式成交 |
| `GET /v1/portfolio-reviews` | 无 | 读取本地追加式复盘 |

`ManualOrderRequest`：`order_id` 必填非空；`local_code` 必须六位数字；`exchange` 为 `SH/SZ/BJ`；`name` 可选；`side` 为 `buy/sell`；`ordered_at` 必须带时区；`quantity` 为有限正 Decimal；`limit_price` 可选且为正；`strategy_version_id`、`recommendation_id`、`note` 可选。重复/非法 ID 或卖出超过持仓等错误返回 `PORTFOLIO_ORDER_REJECTED`。

`CandidateTradeRequest`：`order_id`、`fill_id`、`selection_candidate_id`、证券代码/交易所、下单/成交时间、数量和价格必填；成交时间不能早于下单时间，候选证券必须匹配；写入失败不会留下单边记录。

`ConfirmedManualTradeRequest`：`order_id`、`fill_id`、证券代码/交易所、方向、下单/成交时间、数量和价格必填；`tracking_case_id` 可选，卖出不因没有跟踪案例而拒绝；卖出必须提供 `sell_reason`；成交时间不能早于下单时间；写入失败不会留下单边记录。当前持仓/交易记录页的合并录入表单使用该接口并自动生成两个 ID。

`ManualFillRequest`：`fill_id`、`order_id` 必填非空；`filled_at` 带时区；`quantity`、`price` 为有限正 Decimal；`commission` 和 `stamp_duty` 可选，默认 `0` 且不得为负；`note` 可选。成交必须关联可接受订单，错误返回 `PORTFOLIO_FILL_REJECTED`。

`PortfolioReviewRequest`：`review_id` 必填非空；`symbol` 必须为合法 `CODE.EXCHANGE`；`reviewed_at` 带时区；`note` 必填非空；`recommendation_id` 可选。

### 8.3 单证券持仓历史净收益率

持仓工作区不展示组合级金额表现图。用户点击当前持仓行后，在既有 `StockDetailDrawer` 中打开“表现”标签；该标签按需读取单证券接口。无活动持仓时不提供该标签，也不会发起表现请求。

接口：

```text
GET /v1/workbench/stocks/000001.SZ/performance
GET /v1/workbench/stocks/000001.SZ/performance?as_of=2026-08-25T17:00:00+08:00
```

`symbol` 必须是规范化 `CODE.EXCHANGE`；`as_of` 可选，若提供必须是带时区的 ISO-8601 时间。接口只纳入该证券成交时间不晚于 `as_of` 的已确认订单/成交，以及 `available_at <= as_of` 的 `approved`、`request_kind=market_daily` 快照；不联网、不创建 provider、不启动任务、不写新账本。不同证券不会合并为组合曲线。

响应中的 `daily_return`、`cumulative_return`、`latest_daily_return`、`latest_cumulative_return`、`highest_return` 和 `maximum_loss_return` 均为 Decimal 比例，`0.1` 表示 10%；收益率分母为累计买入现金成本并包含买入费用。卖出按平均成本重放，并计入每笔 `ManualFill` 的 `commission` 与 `stamp_duty`。最高值只取正峰值，最大损失只取负谷值，均返回对应日期。

若截至 `as_of` 没有该证券的已确认成交，或该时点已无活动持仓，接口返回明确状态/原因且百分比字段为空。活动持仓缺少可见行情时返回 `incomplete`/`unavailable` 和具体原因，受影响的估值点百分比保持为空；不得用零、旧价格或外部行情补齐。每个估值点还返回 `market_snapshot_ids`，作为行情证据。

前端表现面板同时使用状态文字、百分比摘要、带标题的原生 SVG 累计净收益率走势和逐估值日语义表格；曲线缺失点保持断开，表格在窄屏下仅在自身容器滚动，页面不横向溢出。表现面板只读，不改变订单、成交、持仓或行情事实。

### 8.4 公式、通达信批次和候选

`POST /v1/formulas` 的 JSON：

```json
{
  "name": "趋势选股",
  "version": "v1",
  "description": "收盘后趋势条件"
}
```

`name` 必填非空；`version`、`description` 可选。公式 ID 按名称和版本内容生成；编辑必须创建新版本，不原地修改。

`POST /v1/selection-batches` 的 JSON：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `content_base64` | 是 | 有效 Base64；解码后是 UTF-8/GB18030 的 TDX 导出 |
| `selection_date` | 是 | 日期 |
| `exported_at` | 是 | 带时区 datetime |
| `source_filename` | 否 | 只能是文件名，不能含 `/`、`\`、换行或 NUL |
| `formula_id` | 条件必填 | 与 `formula_name` 二选一；传 ID 时必须是启用公式 |
| `formula_name` | 条件必填 | 未传 `formula_id` 时必填 |
| `formula_version` | 否 | 未传 `formula_id` 时作为批次元数据 |
| `formula_sha256` | 否 | 64 位十六进制 |

API 导入时 `imported_at` 由服务器取当前 UTC，不接收调用方传入；API 不联网。

`POST /v1/selection-batches/manual` 的 JSON：`selection_date`、带时区的 `recorded_at`、启用的 `formula_id`、非空 `candidates` 数组。每个候选字段为 `local_code`（恰好六位数字）、`exchange`（`SH/SZ/BJ`）、可选 `name`、可选 `note`。重复的代码+交易所会被拒绝；至少一条候选才能创建。

`POST /v1/selection-batches/{batch_id}/labels` 的 JSON：`candidate_id`、`decision`（四种旧版枚举）、带时区 `labeled_at`、可选 `note`。该接口只用于兼容旧证据。

`POST /v1/selection-batches/{batch_id}/annotations` 的 JSON 必须包含 `candidate_id`、`reviewed_at`、`overall_score`（1—5）、`outlook`（`bullish/neutral/bearish`）和 `decision`（`discard/watch/prepare_buy`）；位置、形态、量价、板块标签可多选，备注可选。每次提交追加一条评审，批次归档后不能新增；评审时间不能早于导出时间。

`POST /v1/selection-batches/{batch_id}/exclusions` 的 JSON 为 `candidate_id`、带时区 `excluded_at` 和必填 `reason`，用于独立记录数据无效，不等同于投资决策。

`GET /v1/selection-observation-pool` 支持 `review_state`（`unreviewed/discarded/watching/preparing`）、`batch_id` 和 `include_excluded` 筛选。

`GET /v1/selection-batches/{batch_id}/candidates/{candidate_id}/analysis` 可选 query `tracking_policy_id`；不传时若历史证据包含多个政策会返回 `TRACKING_POLICY_REQUIRED`。该接口只读本地结果。

`GET /v1/workbench/candidates/{candidate_id}/observation-performance` 按候选读取当前连续观察周期的完整表现。`candidate_id` 必须是当前可见候选；`as_of` 可选，若提供必须是带时区的 ISO-8601 时间。响应包含 `candidate_id`、`symbol`、`as_of`、`status`、`started_at`、观察锚点（`anchor_snapshot_id`、`anchor_session_date`、`anchor_available_at`、`anchor_close`）、最新摘要（`latest_session_date`、`latest_daily_return`、`latest_cumulative_return`）和 `points`。每个 `points` 项包含交易日、状态、快照/可用时间、收盘价、`daily_return`、`cumulative_return` 和 `reason`；比例值为 Decimal 比例，例如 `0.012` 表示 1.20%，不是金额。

观察起点是 `as_of` 时点当前连续 `watch`/`prepare_buy` 状态段的首条 `reviewed_at`；同一选股日期、同一标准化证券的跨策略候选共享评审状态和观察起点，`discard` 结束该评审组旧周期，不同选股日期仍隔离周期。锚点取观察开始时已经可见的最后一个有效 approved `market_daily` 收盘价（`available_at <= started_at`）。起点交易日累计涨跌幅为 0，日涨跌幅为空；后续交易日按相邻有效收盘价计算 `daily_return_d = close_d / close_previous - 1`，累计涨跌幅始终按锚点计算 `cumulative_return_d = close_d / close_anchor - 1`，不通过累计值相减推导日涨跌幅。

明细只读取本地 approved、`request_kind=market_daily` 行情和截至 `as_of` 可见的人工事实，不访问 provider、不创建任务、不写每日记录。证券日期按上海时区解释；非交易日不生成点位。缺失、晚到、不可读或无效行情，以及零收盘价除数，会返回 `incomplete`/`unavailable` 和原因，受影响比例为空；不补 0%、不沿用旧价、不跨缺口计算。没有当前连续观察周期时接口仍返回明确的 `unavailable` 状态。

### 8.7 主板行情同步任务

旧的 `POST /v1/market-sync/main-board` 仍是同步兼容入口。新前端和长时间运行场景使用本地耐久任务：

| 方法和路径 | 输入/行为 |
| --- | --- |
| `POST /v1/market-sync/tasks` | 提交 `session_date`、可选 `minimum_coverage`、`max_retries`、`timeout_seconds`；创建幂等任务，不启动后台线程，不发起行情请求 |
| `GET /v1/market-sync/tasks` | `status`、`page`、`page_size` 可选；返回稳定任务视图和 `page/page_size/total/has_next`，不暴露数据根目录或凭证 |
| `GET /v1/market-sync/tasks/{job_id}` | 读取任务状态、尝试次数、更新时间和安全结果摘要 |
| `POST /v1/market-sync/tasks/{job_id}/cancel` | 仅 `queued` 可取消；运行中或终态返回 `MARKET_SYNC_TASK_NOT_CANCELLABLE` |
| `POST /v1/market-sync/tasks/run` | 显式执行一次 runner；按顺序处理排队/重试任务，不注册服务内定时器 |

任务状态为 `queued`、`running`、`retrying`、`completed`、`partial`、`failed` 或 `cancelled`。网络/连接/限流/超时错误在有限重试范围内进入 `retrying`；质量门拒绝、参数/存储错误等进入终态。任务执行期间复用一个可关闭的 Tushare transport，完成或失败后释放连接。任务账本、原始响应、Parquet、manifest 和追加事件文件是审计证据，DuckDB 只作可重建读投影。

#### 8.7.1 Windows Task Scheduler 的显式 runner

Task Scheduler 只负责调用一次显式脚本 `backend/scripts/run_main_board_market_sync_jobs.py`。不要调度 `start.py`、Uvicorn，也不要把 HTTP `/v1/market-sync/tasks/run` 当作调度动作；FastAPI 进程只入队、查询和响应显式执行请求。runner 顺序读取 `LocalJobStore`，本身不创建服务内后台线程或定时器。

任务计划中的“操作”可复制为以下 PowerShell 形式；将尖括号路径替换为本机绝对路径，不要把尖括号原样保存：

| Task Scheduler 字段 | 值 |
| --- | --- |
| 程序/脚本 | `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` |
| 添加参数 | `-NoProfile -NonInteractive -ExecutionPolicy Bypass -Command "$env:PYTHONPATH='<BACKEND>\src'; $log='<DATA_ROOT>\logs\main-board-market-sync.log'; New-Item -ItemType Directory -Force (Split-Path $log) > $null; & '<UV_EXE_ABSOLUTE>' run --project '<BACKEND>' python '<BACKEND>\scripts\run_main_board_market_sync_jobs.py' --data-root '<DATA_ROOT>' --limit 1 *> $log; exit $LASTEXITCODE"` |
| 起始于 | `<BACKEND>`，即仓库的 `backend` 目录 |

其中：

- `<BACKEND>` 必须是包含 `pyproject.toml` 的 `backend` 绝对目录；动作显式设置 `PYTHONPATH=<BACKEND>\src`，避免 Task Scheduler 的环境与交互式终端不同而找不到包。
- `<UV_EXE_ABSOLUTE>` 使用执行账户运行 `where.exe uv.exe` 得到的绝对路径；不要依赖 Task Scheduler 的有限 `PATH`。
- `<DATA_ROOT>` 必须与 API 入队时使用的同一个绝对数据根目录。任务 payload 已经保存入队时的 `market_root`/`universe_root`，runner 不会用另一个根目录覆盖它们；移动数据根目录前应先完成迁移和队列核对。
- `--limit 1` 使每次计划触发最多处理一个任务；空队列返回 `jobs: []` 并以退出码 `0` 安全结束。所有处理结果没有失败任务时退出码为 `0`；存在 `failed` 任务时脚本返回 `2`，应由任务历史或日志告警。
- 日志目录需可由任务账户写入。脚本 stdout/stderr 追加到 `<DATA_ROOT>\logs\main-board-market-sync.log`；日志只用于状态、结果摘要、路径和已脱敏错误，不应写入原始 provider 响应或凭证。
- `TUSHARE_TOKEN` 不得出现在“添加参数”、任务 XML、日志路径、重定向内容或任何示例中。需要执行非空队列时，凭证只由任务执行账户在动作之外的受控环境提供；不要在命令行、脚本文件或任务定义中写入 token 值。空队列 smoke test 不需要 provider 凭证。

#### 观察池表现和雪球日线链接

“观察池”列表保持轻量：每条分页记录只返回 `observation_performance` 摘要，包括观察起点、起点价、累计涨跌幅、状态和原因，不内嵌无界逐日历史。点击某一行后，详情抽屉保留被点击的 `candidate_id`；仅对当前 `watch`/`prepare_buy` 候选显示“观察表现”页签，并按需调用候选级明细接口。

观察周期按同一选股日期和标准化证券的评审组、当前连续状态段隔离；同日跨策略候选共享状态和起点，最新 `discard` 会结束旧周期并在重新观察时重新起算，不同选股日期仍独立。详情页展示观察锚点、逐交易日收盘价证据、日涨跌幅、观察期累计涨跌幅和每个点位的状态/原因，并用原生 SVG 绘制观察期累计涨跌幅折线。折线只连接连续可用的累计比例点，缺失证据以断开、状态和明细呈现，不补点。摘要同时展示可用累计比例中的最高涨幅、最大跌幅及对应交易日；最大跌幅是累计比例最小值，不等同于峰值回撤。鼠标悬停或键盘聚焦图表数据点时，会显示交易日、收盘价、日涨跌幅和观察期累计涨跌幅；缺失字段显示不可用。比例按 Decimal 比例解释并格式化为百分比，不展示金额、持仓市值、手续费或持仓净收益。

列表摘要和明细都只读取本地 approved、`request_kind=market_daily` 行情；明细 API 的完整字段、`as_of`、可见性和计算规则见上面的候选级接口说明。annotation、排除事实和列表相关成交均按 `as_of` 截断；行情 `available_at` 晚于观察起点或查询时点、快照不可读、收盘价无效或中间交易日缺证据时，页面显示 `—` 与 `incomplete`/`unavailable` 原因，不补 0%、不沿用前值，也不跨缺口计算日涨跌幅。

股票详情抽屉中的“查看日线 K 线”仅是雪球外部导航，不是应用内行情证据。标准证券代码按 `CODE.EXCHANGE` 转成雪球 `EXCHANGE+CODE`，例如 `000788.SZ` 对应 `https://xueqiu.com/S/SZ000788`；链接在新标签页打开并使用 `rel=noreferrer`，应用不会请求或缓存雪球数据。

持仓详情的“表现”页签同样提供累计净收益率折线图。鼠标悬停或键盘聚焦可用数据点时，提示显示估值日、approved 行情收盘价、日净收益率和累计净收益率；不可用行情不补零或沿用旧值。提示默认隐藏，命中数据点后保持显示，即使鼠标移出或焦点离开；命中下一个数据点时更新，关闭详情或次级图表页时清除。图表增加“放大查看图表”入口，在应用内次级图表页以更大尺寸展示；关闭后返回股票详情，不重复请求行情。

## 10. 结果、状态和常见误区

### 10.1 成熟结果

当前结果政策默认 ID 为 `outcome-fixed-10-net-positive-v1`，研究基线为：

- 收盘后信号，后续 3 个交易日入场窗口；
- 日线触达是成交近似，开盘成交和最高/最低触达规则由 `entry-limit-chase-v1` 明确记录；
- 固定持有 10 个交易日退出；
- 不启用止盈/止损；
- 扣除费用后净收益大于 0 为 `win`，等于 0 为 `flat`，小于 0 为 `loss`；
- 未触发入场为 `no_entry`，行情不足或质量失败为 `unresolved`；
- 沪深主板数量按 100 股整手向下取整，默认名义金额为 10000 元。

命令行中的 `--horizon-sessions`/API 中的 `horizon_sessions` 可以创建新政策指纹；它不会修改旧结果。

### 10.2 成熟任务状态

成熟任务的状态为 `queued`、`running`、`completed`、`partial`、`failed`；只有网络、限流、超时和连接错误被视为可重试。主板同步任务还会使用 `retrying` 表示有限重试等待；质量门、参数错误、快照冲突和股票池不一致不会自动重试。主板同步取消只允许 `queued`，不会取消已开始执行的任务。

### 10.3 不要把这些概念混为一谈

| 误解 | 实际行为 |
| --- | --- |
| “我已经有本地单票 Parquet，所以成熟不会联网。” | 错。provider 模式先调用适配器；只有 approved-snapshots 任务保证离线。 |
| “日历文件存在，所以任何日期请求都不用联网。” | 只有请求范围在 manifest 覆盖边界内才不用联网；缺口会增量拉取。 |
| “同一内容 snapshot ID 相同，所以 provider 没有被调用。” | 错。单票 ingest 可能先远程获取，再因内容相同复用 snapshot 文件。 |
| “全市场快照存在但被拒绝，也能作为缓存。” | 错。只有 `approved` 快照可消费；拒绝快照会导致重新同步或报告阻断。 |
| “复权因子缺失可以顺手抓日线。” | 错。批量因子补齐只消费已批准的同日全市场日线。 |
| “模型分数就是胜率。” | 错。未校准分数不能称胜率；API 固定返回 `authoritative=false`。 |
| “当前股票池可以回答历史日期搜索。” | 错。没有该时点已知快照时返回 `UNIVERSE_SNAPSHOT_NOT_FOUND`。 |

## 11. 排错顺序

1. 先查看命令的 JSON 输出和退出码：`0` 成功，`1` 通常表示质量/准入/比较门未通过，`2` 通常表示输入、provider 或存储错误。
2. 看到“未联网”预期时，检查入口是否为 `approved_snapshots`、是否命中批准快照联合键，以及 calendar manifest 是否覆盖请求区间。
3. 看到 `TUSHARE_TOKEN is not set` 或 `WAIZAO_TOKEN is not set`，先检查当前启动该进程的环境，不要把 token 写进参数或文件。
4. 看到质量拒绝时，先读取对应 `data/**/quality/*.json`，不要直接删除快照重跑；删除会破坏定位，应该使用新的输出或保留原证据。
5. 看到 `UNIVERSE_SNAPSHOT_NOT_FOUND`，先创建与 `as_of`/`known_at` 匹配的时间点股票池，不要将当前股票池复制到历史日期。
6. 看到成熟任务 `queued` 且 `retryable=true`，再次执行任务；如果是 `market_snapshot_quality_rejected`、快照不匹配或参数错误，先修复输入而不是增加重试次数。
7. 看到前端“请求失败”，优先检查 `/healthz`、前端 `VITE_API_BASE_URL`/Vite 代理和后端工作目录；前端不会把错误分数或最新行情填充进页面。
